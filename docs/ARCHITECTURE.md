# How CalibreFast works

See also: [FEATURES.md](FEATURES.md) for behaviour, [SECURITY.md](SECURITY.md) for the access model, and [notes/Performance.md](notes/Performance.md) for performance notes.

## Packages

Self-contained code lives in packages under `pkg/`, each with a README. The app itself is `package main` at the root; a package never imports it, and never touches the app's databases, flags, catalog or users: what it needs is passed in.

- [`pkg/xml11`](../pkg/xml11): lets `encoding/xml` read XML 1.1 documents.
- [`pkg/epubzip`](../pkg/epubzip): the package document, entries and declared cover of an EPUB's zip.
- [`pkg/opf`](../pkg/opf): reading and writing OPF metadata (`metadata.opf`), series, identifiers, languages. Main uses aliases (`OPF`, `OPFMetadata`, `opfIdentifier`, `opfMeta`) for its types.
- [`pkg/langcodes`](../pkg/langcodes): language names and canonical codes.
- [`pkg/isbn`](../pkg/isbn): checking ISBNs and finding them in EPUB, MOBI/AZW3 and PDF text.
- [`pkg/metalookup`](../pkg/metalookup): Open Library and Google Books clients, with limits and a cache.
- [`pkg/hardcover`](../pkg/hardcover): Hardcover's GraphQL API for series and their books, with a budget that holds work over the plan's limits instead of refusing it.
- [`pkg/kosync`](../pkg/kosync): KOReader progress sync protocol pieces (document ids, keys, errors).
- [`pkg/koreader`](../pkg/koreader): KOReader's XPointers ↔ EPUB CFIs, its annotations file, its Lua files. `pkg/koreader/koreadertest` has EPUB fixtures.
- [`pkg/imageutil`](../pkg/imageutil): covers, thumbnails, a PDF's first-page picture.
- [`pkg/filehash`](../pkg/filehash): cached SHA-256 of files.

## Data sources

- **`metadata.db`** (Calibre's SQLite database) is the index for listing, searching and filtering.
- **Series** (`series.go`; the OPF side in `pkg/opf`) come from `metadata.db` (through the catalog) wherever they're shown or used: the book page, the editor's current values, next in series. The editor writes both: one `books_series_link` row and `books.series_index`, and `calibre:series`/`calibre:series_index` in the OPF; files' series are read from those meta, or EPUB 3's `belongs-to-collection`.
- **`metadata.opf`** in each book folder is what the book page and the metadata editor read. Edits write both. The editor never sees library identifiers (`calibre`, `uuid`, a scheme-less `urn:uuid:`: `opf.IsLibraryIdentifier`), and a save keeps the book's own as they are (`updateBookInCalibreDB`).
- **`calibrefast-groups.json`** in the library root holds user-defined groups. It's the only file CalibreFast adds to a library. (The Recycling Bin is outside the library, in `-datadir` by default.)

## Main library pages

On startup CalibreFast queries `metadata.db` and writes paginated JSON (`pages/page1.json`, `page2.json`, …, `booksPerPage` = 60 books each). The frontend fetches these directly as static files, so browsing never hits the database. After uploads and imports the pages are written again from the catalog (`refreshLibraryPages`; below), in order and only where a file's contents change, so a new book shifts the others along and the count includes it. Edits (the editor, the bulk editor, a new cover) don't change the order, so only the pages holding the edited books are patched (`refreshPagesFor`: the Latest pages from `bookPages`, the Shuffle page from the book's place in the order), instead of comparing every page (about a quarter of a second at 100k books). Removing or restoring a book edits only the pages that hold it (`library_pages.go`).

Each book's `authors` is its authors' names in Calibre's order, `A & B` (`bookAuthorsSQL` in `authors.go`), in every grid: not `books.author_sort`, which is the "Last, First" sort form. `authors.go`'s `splitAuthors` reads author lists (editor, uploads) on `&` only; `web/authors.ts` reads the editor's field the same way. Other ways of writing them (`;`, `Last, First`) are only rewritten by the editor's Split button (`tidyAuthors`).

**The catalog** (`catalog.go`): the same startup pass reads every book's grid entry, tag, author and series ids, `has_cover` and formats (`data` table) into memory, one sequential read per table; the pages are written from it. Readers take the current `*catalog` without locking. The write paths call `catalogChanged(uuids)` / `catalogRemoved(uuids)`; queued changes are applied together (`catalogFlush`, at most every 250 ms) by re-reading only those books through the link tables' indexes and swapping in an updated copy. Removed books stay as tombstones until the next startup, like the page gaps below. `booksByUUIDs` (every `/me/*` list and shelf), `bookExists` and `resumeURL` answer from it, reading `metadata.db` (or listing the book's folder) only for books it doesn't have yet. The library may be on slow or network storage, so page loads shouldn't touch it: `libraryIO` (`library_io.go`) counts statements prepared on `metadata.db` (an SQLite authorizer on the `sqlite3_calibre` driver) and the cover and folder reads under `-basedir`, and tests check it stays put. A book found to have no `cover.jpg` is remembered (`noCover`) until its cover or entry changes, so its thumbnail isn't looked for again.

**Discover** (`discover.go`, `templates/discover.html`, `web/discover.ts`; `/`): the same page for everyone, built from memory (counts from the aggregate caches) and filled by the script from the static page files: the Shuffle row walks `pages/shuffle/` a strip per load or Shuffle click, with its state in localStorage (`cf-shuffle`: `{version, starts, next}`, `starts` the strips shown, which Previous steps back through, up to 20; a new `pagesVersion` starts somewhere random), skipping the user's finished books (reading.ts's marks); Recently added is the start of `pages/page1.json`. Cards are `renderBookCard`'s, covers `coverUrl`'s (the same URLs as the grid), loaded on screen first (`web/cover-limits.ts` is shared with the grid). The sign-in line shows only when `cf-me` (nav.ts) says nobody is signed in. What's the user's comes from one request, `GET /api/me/home` (`home.go`): the marks (`userReading`, the same as `/api/me/reading`, which the page no longer asks for), and the Continue reading and Want to read rows (20 each, with counts), ordered by the newer of the status change and the last position from any device; books from the catalog. The answer is kept in localStorage (`cf-home`) and painted at once next time. Signed out, Continue reading is this device's: `web/local-reading.ts` keeps an index of the guest positions (`cf-local-reading`; the readers update it, and it's built once from existing `cf-progress-*` keys), and `GET /api/books?uuids=` (catalog only, up to 50; an unknown id costs no read of the library) gives the books. Books read to 97% or more (`finishedPercent`, as the readers mark them) count as finished on the device, for Shuffle.

**Shelf and tag rows** (`shelf_pins.go`): a user's pinned rows are their `shelf_pins` (pinned = 1) and `tag_pins`, ordered together by one `position` numbering, then the featured shelves (`shelves.featured_pos`) they have no row for. Unpinning a featured shelf stores pinned = 0, which outlasts re-featuring. A reorder (`PUT /api/me/pins` with `rows`) stores every row shown, so the user's order is stable. A shelf row's books are its first 24 (one windowed query), a tag row's 24 of its books in the shuffle order, both from the catalog. Signed out, `pages/discover/featured.json` holds the featured shelves, written at startup and on any change to a global shelf or the catalog, only when it differs, and cached for good under a hash of its contents (`featuredVersion`). `web/reorder.ts` (drag, with Move up/down buttons) orders the home page's rows and the lists on `/shelves`.

**Tag rows** (`tag_rows.go`): every eligible tag (after groups) gets `pages/discover/tag-N.json`, 24 of its books in the shuffle order; their index is in the Discover HTML and their stamp is a hash of the files (`servePages` caches them under it). Eligible: included by an admin (`discover_tags`), else the 40 biggest of the tags with at least 3 books on at most `discover.broad_tag_share` (`settings`, 25% by default) of the library; never excluded ones. Rewritten at startup, after catalog changes, on tag group changes and on settings changes. Each "More in" row takes its tag when it nears the screen: the user's affinity tags first, then a weighted random pick, skipping pinned tags.

**Recommendations** (`recommend.go`): on each `/api/me/home`, from an index of the catalog's tags (after groups, without excluded ones) and series, made once per catalog, groups version and tag-settings version. Next in series: the book after the furthest one read in each series. Then tag affinity: each tag on the user's books scores their weights (starred 3, reading/finished 2, wanted 1) times its idf; candidates are the top tags' books (bounded), scored by their tags, plus an author bonus and a little jitter; marked books are left out. The answer's `tags` (the three strongest) lead the tag rows.

**Bringing guest reading into an account** (`guest_import.go`, `web/guest-data.ts`, `web/account-import.ts`, `/account/import`): `guest-data.ts` collects the guest records (the plain-named `cf-progress-*`, `cf-annotations-*`, `cf-bookmarks-*` keys) and `nav.ts` offers them after sign-in (declined for good per account in `cf-guest-import-declined`, put off for the visit in sessionStorage). `POST /api/me/import/preview` compares each book with the account and writes nothing: `new`, `same` (the same position and highlight ids: an older copy of the account's own), `conflict` (the device's newest position against `latestProgress`, any device), or `missing`. `POST /api/me/import` stores the chosen books one step at a time, each repeatable: new highlights (`storeAnnotation`), notes merged into the account's highlight of the same anchor, new bookmarks (`ON CONFLICT DO NOTHING`), and the position when chosen (written as the newest when it's older than the account's) with the status the readers would set. No transaction: the app database has one connection, and the helpers use it; a retry finishes a partial import. The reader's Sign in (`offerSignIn`, `reader-chrome.ts`) goes to `/login?next=<the reader>?…&sync-guest=1`; back in the reader, signed in, `syncGuestBook` (`guest-sync.ts`) adds the book's guest records before the place is loaded, or, if the account's place differs, goes to `/account/import?book=<uuid>&next=<the reader>`, which asks for just that book and returns. Only a sign-in from the reader does this without the review. Registration follows `next` as signing in does (`safeNext`). The grid itself is at `/latest`; `/?page=N` redirects there.

**Shuffle** (`shuffle.go`, `/shuffle`): the catalog holds a random order of its books, made at each start (`randomOrder`); books added while running go at the end. `pages/shuffle/pageN.json` are written from it with the library pages, only where a file changes, so an upload rewrites only the last one; removing or restoring a book rewrites them (`refreshShufflePages`), since a random order can't keep gaps. Signed out, `/shuffle` is the library grid over those files. Signed in, it's a list (`serveUUIDList`) of the same order without the books the user finished, built from the catalog and one `reading_status` query: nothing is read from the library.

**The catalog's snapshot** (`catalog_snapshot.go`, `<cachedir>/catalog.snap`, gob): a start whose `metadata.db` matches the snapshot's key (size, modification time and the header's change counter, plus any `-wal`'s size and time) takes the catalog from it: a `stat` and a 28-byte read instead of reading every table. It's saved after a full read, under the key taken before that read, and 5 s after changes are applied. Only CalibreFast's own changes, told to the catalog, are folded in: a commit by anything else (Calibre desktop) changes `PRAGMA data_version` on `calibreDB`, and the snapshot is then removed and not saved again that run, so the next start reads the library. A rollback journal beside `metadata.db` means it isn't settled: no snapshot is used or saved then. The page files are written from the catalog either way, only where their contents differ.

`index.html` asks for `pageN.json?v=<pagesVersion>`, a stamp that changes whenever the files are rewritten, so with a matching `v` they're cached for good (`servePages`). Anything else is revalidated.

## Filtered views, overview pages and search

- These query SQLite directly.
- **Pre-computed at startup and refreshed after uploads, edits and group changes:**
  - the overview lists (with groups collapsed and distinct book counts)
  - each filtered view's page count, cached in memory
- **Categories.** Authors, publishers, tags, languages and series are described in one table (`categories` in `aggregate.go`), so all five share the same pages and endpoints. Languages differ only in their column names (`lang_code`); a series lists its books in series order (`bookOrder`).

## Frontend

- **TypeScript and CSS, built by Go tools.** Browser code is TypeScript in `web/`, along with the stylesheets: `web/style.css` for the app, and `web/auth.css`, for the pages seen before signing in (`login.html`, `link.html`): just what they use, so signed-out visitors don't get the whole app's styles. `TestAuthCSSOnlyNamesAuthPageClasses` keeps it to those pages' classes. On a private server it's the only `/static/` file served without a session (`isPublicPath`); the rest, `/sw.js` and `/offline` answer 401. There's no Node, npm or `package.json`.
  - `go generate` runs two steps, both pinned as Go tools in their own module, `tools/go.mod`, so the server itself still builds with Go 1.25 and none of their dependencies. Working on the browser code needs Go 1.26+, which `tsgo` requires.
    1. `tsgo`, the Go-native TypeScript compiler, type-checks `web/` (`tsconfig.json`: strict mode, no unused locals/parameters, every file is a module). It writes nothing.
    2. `tools/jsbuild` uses esbuild's Go API to bundle each entry with its imports, minify it, and write it to `static/dist/` named by content hash (`app-htmx-NGM5EDXU.js`), with a source map and `manifest.json`.
  - **Entries are what the templates use**, via `{{ asset "app-htmx.js" }}` (`web/app-htmx.ts`) or `{{ asset "style.css" }}` (`web/style.css`). Inline module scripts import the same way: `import … from {{ asset "metadata.js" }};`. jsbuild finds the names by scanning `templates/`, so adding a script to a page is just the template change plus `go generate`.
  - One file per page script, with no import waterfall. Code shared by two entries is copied into both, so module state isn't shared between them: e.g. the book modal's user controls come bundled inside `app-htmx.js`, and `book.html` loads `user.js` only when the page is opened on its own.
  - `static/dist/` is committed, so `go run -tags sqlite_fts5 .` works without a build step. **Don't edit it by hand.** `TestTypeScriptUpToDate` type-checks and rebuilds into a temporary directory and fails if the result differs from the committed files.
  - To update the tools: `cd tools && go get -tool github.com/microsoft/typescript-go/cmd/tsgo@latest` (or `go get github.com/evanw/esbuild@latest`), then `go generate` and run the tests.
- **Third-party libraries** (htmx, JSZip, epub.js, DOMPurify, pdf.js) are committed in `static/vendor/<package>@<version>/`: the files the pages use, at their paths in the npm package, plus its license. Templates link them by path; scripts that load one themselves take the path from `web/vendor.ts`, which esbuild leaves alone. Serving them ourselves saves a cold page load the DNS, TCP and TLS of another host, and browsers no longer share a CDN's cache between sites anyway.
  - `TestVendor` checks that every `/static/vendor/` path in `templates/` and `web/` exists, that every package is used, and that no script comes from another host.
  - pdf.js fetches what a document needs, a file at a time: WebAssembly image decoders (JPEG 2000, JBIG2) from `wasm/`, character maps for CJK fonts from `cmaps/`, the 14 standard fonts (which PDFs may use without embedding) from `standard_fonts/`, and a CMYK profile from `iccs/`.
  - To upgrade a library: download `https://registry.npmjs.org/<package>/-/<package>-<version>.tgz`, check it against `dist.integrity` from `https://registry.npmjs.org/<package>/<version>`, copy the same files into a new `<package>@<version>/`, update the paths, and delete the old directory.
  - Shared code: `web/dom.ts` (typed element lookups, `api()` fetch helper) and `web/types.ts` (shapes of the JSON the Go server sends; keep in sync with the Go structs named there). `web/globals.d.ts` describes the parts of htmx, epub.js and pdf.js the app uses.
- **Readers** (`/read`, `/read-pdf`). `templates/reader-parts.html` holds what both pages share; `web/reader.css` is their only stylesheet.
  - `web/reader-chrome.ts`: the top and bottom bars (they slide away together while reading; the page never reflows), the sidebar (Contents, Bookmarks, Search) and the settings sheet, and the theme.
  - **Preview** (`web/reader-preview.ts`, `?preview=1`, or `?import=<id>` for a book in the import queue): the metadata editor's **Read** button (`previewReadLink`). Nothing is saved: no position (which would set the reading status), bookmarks, highlights or kept copy, and the service worker doesn't keep the page. `ReaderPageData.Preview` marks the page (`data-preview`), which hides the bookmark and notes controls. Back closes the tab (`leaveReader`): the editor opens it with `window.open` so a script may close it, and in-book jumps add no history entries (`keepsHistory`). If the browser won't close it, the status says so, unless no page of the library led there (no same-origin referrer, no opener): then Back goes to the editor (`ReaderBook.editor`). Outside previews, Back steps back past the in-book jumps when a library page is behind them (`history.length` and a same-origin `document.referrer`), and otherwise goes to the book's page (`/book/get/<uuid>`).
  - `web/reader-settings.ts`: reading settings, per device, in `localStorage` (`cf-reader-settings`). A control binds to a setting by attribute (`data-setting`, `data-value` or `data-step`), so a new setting is a default there plus markup.
  - **Themes** are sets of CSS variables on `:root[data-theme]`: `--page-*` for the book, `--chrome-*` for the bars. An inline script sets `data-theme` before the first paint. EPUB chapters are iframes, so `web/reader.ts` adds a stylesheet of its own to each (`contentCss`: colours read back from the variables, font, size, line height, alignment, hyphenation) through epub.js's content hook; the size is the root's, and the same hook turns the chapter's absolute font sizes (pt, px, keywords like `small`, in its stylesheets and `style` attributes, `!important` kept) into rem (`relativeFontSizes`, 12pt = 16px = 1rem), so books that set them follow it while relative sizes keep their proportions; settings that change how much fits on a page lay the chapter out again at the same place (`rendition.resize()`).
  - **Opening an EPUB** (`web/reader.ts`):
    - **In parts:** `web/epub-source.ts` reads the `.epub`'s zip directory from its end with an HTTP Range request to `/download/{uuid}/epub` (`http.ServeFile` handles ranges), then each file epub.js asks for with one more range, inflated by the browser's `DecompressionStream`. `If-Range` keeps the reads to one version of the file.
    - **epub.js glue** (`web/epub-open.ts`): epub.js is handed a book root that is never fetched (`/epub-virtual/{uuid}/`) and a `requestMethod` that reads from the source. Its own resource replacement is off, because it would read every image before the first page. A serialize hook points each chapter's images, media, stylesheets and their fonts at `blob:` URLs as the chapter is rendered.
    - **The rest of the book** downloads in the background: at once for books under 3 MB, otherwise after the first page. From then on every read is from memory, and page numbers (`locations.generate`) and search, which need every chapter, run.
    - **Kept in the browser** (`web/book-cache.ts`, IndexedDB `cf-books`): the whole file, its `Last-Modified` and the generated page numbers, so reopening needs no download (a `HEAD` checks for a newer file). What stays, and for how long, is `web/retention.ts`, by the user's preferences for that device (`web/prefs.ts`, set on `/preferences`): Reading books until unopened for N days (default 7), the most recent few (default 5) kept regardless; the first N books (default 3) of Discover's "On deck / Saved for later" row downloaded ahead of time (`GET /api/me/saved-books?limit=N`: the On deck books, the next in a series, which count as Saved for keeping; then Saved, oldest first, so saving more books doesn't swap one download for another); Finished books for a day; a book set back to Not Reading at once (only on fresh statuses, the grid's `/api/me/reading` answer; the last status seen is kept with the book). A storage limit (the user's, else half the browser's quota, or 1 GB when the browser doesn't say, decided as books are kept) drops Finished books first, then downloads cut off part way, then never-opened Saved copies, then other books not being read; a size limit skips large files. Storage failures are logged to the console with what they mean. `web/book-sync.ts` downloads what's missing (the last N Reading books, then the Saved ones) from the library pages (grids, home, author/series lists, shelves, a book's page), one book at a time and in one tab (a Web Lock; other tabs wait their turn and take over if it closes). Downloads give way to what the reader is waiting for (`web/page-busy.ts`): covers near the screen (one that never loads stops counting after 30 seconds), fetches, htmx's among them (the book popup, the next grid page), on any visible library page, and a reader loading its book. They hold off, are cut off if it lasts (keeping what arrived), and go on once every page has been quiet for a second. They're fetched at low priority. A download cut off keeps what arrived (IndexedDB `partials`, its bytes a record per 1 MB piece in `partial-chunks`, so saving writes only the new piece) and goes on with a Range request; a 206 is used only when its `Content-Range` starts where the kept part ends, and a file shorter than its `Content-Length` is never kept. Each book downloads in one place at a time (a Web Lock per book), so a pin and the queue don't fetch it twice. A download that fails is tried again after a minute, then four times as long each time, up to a day. Partials of books no longer wanted are dropped, and they show on `/preferences`. The top bar's sync button (`web/nav.ts`, state in `web/sync-state.ts`) shows the download's progress and any reading changes not yet sent, and pauses book downloads (the pause in its own localStorage key, so progress written from another tab can't undo it). Pinned books ("keep") must have a status, so pinning one with none adds it to Saved; a pin's download cut off is finished by the queue, first (`pin-downloads`). Kept books are also dropped on sign-out and when someone else signs in.
    - **Reading changes are sent at once, from any page.** The readers send a position as soon as it changes (one request at a time; moves made meanwhile go in the next), and bookmarks and highlights as they're made. What couldn't be sent (no connection, the server down) is sent by `web/send-pending.ts` from every signed-in page (nav.ts) as it opens and the moment the server answers again (`server-watch.ts`, checked every few seconds while it's down). Favorite and reading-status changes go the same way (`web/pending-marks.ts`, `cf-u/<user>/mark-<uuid>`, from the popup's controls in `web/user.ts` and the cover buttons' `coverAction`): changes to a field coalesce into one request, the last, sent with how long ago it was made (`age_ms`, measured on the device, so clocks needn't agree). The server keeps when each user's favorite and status of a book last changed (`mark_changes`, unix ms on its clock, also for an unfavorite or a cleared status, which leave no row; the reader's automatic status changes count too) and applies a change only if it's newer (`claimMarkChange`, one upsert, in the same transaction as the change), answering with the field as it stands and `applied`. Marks from the server (`toMarks` in `web/reading.ts`) and its rendered controls get what waits laid over them, so the cached marks and their tag stay the server's own. Once sent, each change is told to the page as `cf:status`, which is when Discover refills its rows. If `/book/me/<uuid>` takes over 300 ms or fails, `user.ts` builds the favorite and status controls from the cached marks (`data-local`) and loads the server's when it answers. What the server refuses for good (the book gone: 404; 400; 409) isn't kept waiting forever. Only book downloads wait for quiet pages.
    - **Lists kept in the browser are tagged** (`listtag.go`): the reading marks, the Saved list and the offline Reading list carry a hash of the answer (`ETag`, or `reading_tag` on `/api/me?reading=1`). The browser sends back the tag of its copy (`If-None-Match`, or `&have=`) and gets 304 (or `reading_same`) when nothing changed, so a slow connection doesn't carry the same lists again.
    - **Offline** (`web/sw.ts`, served at `/sw.js` by `sw.go` with this build's asset list in front, so each build installs a new one; HTTPS or localhost only). It keeps `/static/` files and opened books' `/read` pages, and kept books' popups (the `/book/get/<uuid>` answer to an htmx request, in `cf-pages`, fetched with the reader page when a book is kept, refreshed when opened online, dropped with the book's last file; served from the cache with the thumbnail's URL changed to `/offline-cover/<uuid>`, which the worker answers from `cf-covers`), and shows `/offline` (`web/offline.ts`) when a page can't be fetched or a proxy answers 502–504. That's the Reading page with no server: the list as signed-in pages last saved it (`web/offline-books.ts`, localStorage `cf-offline-reading`, from `/me/reading?api=1&all=1`), each book's cover from the `cf-covers` cache (read by the page itself), and the books kept in `cf-books` (`web/book-cache.ts`) as the ones that open. It asks `/api/me` every 15 seconds and reloads into the real page once the server answers. A popup that fails for want of the server (`web/modal.ts`, `showFailed`) waits for it through `web/server-watch.ts` and loads the book again when it answers; its **Switch to offline mode** reloads the page, which the worker answers with `/offline`. Per book, `web/offline-control.ts` (on the book page and popup) sets "keep" (downloaded now, skipped by `sweep` and the storage limit) or "never" (the reader's `keepCopy` keeps nothing), in localStorage `cf-offline-prefs`; `web/offline-marks.ts` badges the cards of kept books. The web app manifest (`/manifest.webmanifest`, `sw.go`, linked from every signed-in page by the `appHead` template function) and the icons in `static/icons/` make the site installable. API calls aren't cached: the readers keep their own copies of positions, bookmarks and notes. Covers, page files and API calls skip the worker altogether where the browser supports static routes (Chrome 123+, `addRoutes` at install), so a cached cover isn't held up waking an idle worker.
    - Browsers without `DecompressionStream` download the whole book first and open it with JSZip, as before.
  - **Input** on an EPUB page happens inside the chapter's iframe, so taps, swipes, the wheel and keys are listened for on each chapter's document (`rendition.on("rendered")`).
- **PDF reader** (`web/reader-pdf.ts`). One page or a pair is on screen at a time; `scale` is CSS pixels per PDF point.
  - `web/pdf-view.ts` draws. Each page is a box sized in CSS pixels, snapped to whole device pixels, holding:
    - a **base canvas** of the whole page at `scale × devicePixelRatio`, one canvas pixel per screen pixel. Past 8 million pixels it stays at the largest size that fits and is stretched;
    - only then, a **detail canvas**: the part of the page on screen (plus a margin) at full resolution, drawn through pdf.js's `transform` render option. Its size depends on the window, not the zoom, so any zoom stays sharp and under browsers' canvas limits;
    - pdf.js's **text layer** (`TextLayer`; its CSS is in `reader.css`) and the **links** (`getAnnotations`, drawn as plain `<a>`s). Both are placed in percentages and sized by `--total-scale-factor`, so zooming never rebuilds them.
  - A zoom gesture only changes CSS sizes (the canvases stretch); 140 ms after the last change the canvases are drawn again. Scrolling a zoomed page redraws the detail canvas the same way. New canvases are drawn off screen and swapped in, so nothing blanks.
  - `web/pdf-gestures.ts`: pinch (touch events; `touch-action: pan-x pan-y` leaves one-finger panning to the browser), Ctrl/⌘+wheel and Safari's gesture events, mouse drag, swipe. Zoom is anchored: the point under the fingers is put back under them by scrolling.
  - `web/pdf-loupe.ts`: the magnifier. It asks `pdf-view` to draw a region of the page at the lens's own resolution, as a tile three times the lens's size that slides under it, and draws a new tile near the edge.
  - **No dark page mode.** PDF pages keep their own colours in every theme; only the surroundings and bars change. pdf.js's `pageColors` render option was tried for it and turned down: it remaps images too, so a colour photo comes out as flat greys.
- **Whose local reading data** (`web/local-keys.ts`). Positions, bookmarks and highlights are kept in localStorage per book. Signed out (guest), under the plain names (`cf-progress-<uuid>-<format>`, `cf-bookmarks-<uuid>`, `cf-annotations-<uuid>`); signed in, under the user's own prefix (`cf-u/<username>/progress-…`). Only the signed-in user's records are ever sent, so nothing a guest made reaches whichever account next opens the book on that device; adding guest reading to an account is a separate, deliberate step (planned: [notes/Discover.md](notes/Discover.md)). Offline, the readers use the user `nav.ts` last saw signed in, and send their changes once the server answers. Signing out (`forgetSynced`, from `nav.ts`) drops the user's records the server has and keeps unsent changes under their name. Records written before this split are in the plain names, so they count as guest data: kept, not sent.
- **Highlights and notes.** `web/annotations.ts` is the data and its sync, `web/annotation-ui.ts` the toolbar, note editor and Notes tab; each reader finds selections and draws highlights itself.
  - **Anchors** survive zoom and reflow. EPUB: a CFI range (epub.js's `selected` event gives it, and draws the highlight back from it). PDF: `{"page":N,"rects":[[x0,y0,x1,y1],…]}` in PDF points from the page's top left, one rectangle per line, drawn in percentages of the page under the text layer.
  - **Sync** (`annotations.go`, `GET`/`PUT /api/me/annotations/{uuid}[/{id}]`): ids are made in the browser; every change carries the device's clock and the newest wins. A delete is a change too: the row stays as a tombstone with its text cleared, so a device that was offline drops its copy instead of sending it back. Where an annotation is never changes after it is made.
  - **KOReader** (`koreader_annotations.go`, with the format in `pkg/koreader`; [KOREADER.md](KOREADER.md) has the steps). Its sync protocol has no annotations, but it has a file of its own for moving them between devices, `<book file>.annotations.lua`, which it merges in when a book is opened. `GET`/`POST /api/me/annotations/{uuid}/koreader?format=` write and read that file.
    - `pkg/koreader/lua.go` reads the file as data: a parser for tables, strings, numbers and booleans. Nothing is executed; anything else is a syntax error.
    - `pkg/koreader/text.go` converts exact positions in an EPUB. A CFI counts UTF-16 units of the text as it is in the file; crengine's XPointer counts characters of the text as crengine stores it (line breaks and tabs become spaces, runs of spaces collapse, white space that opens a block is dropped). A chapter is parsed once and a place is a text node and offset, from which either form is written.
    - **Import** uses the CFI newer KOReader saves beside its XPointers; otherwise the XPointers, checked against the highlighted text, and failing that a search for the text near them. Ids come from KOReader's identity for a highlight (place and creation time), so a second import changes nothing, and a tombstone keeps a highlight deleted here from coming back.
    - **Export** dates the file 1970, because KOReader's import removes its own annotations that are older than the file and not in it.
    - A PDF's rectangles are in points from the page's top left on both sides.
- **Top bar.** Every page except the readers uses the shared bar in `templates/topbar.html`: `{{ template "topbar-start" (topbar …) }}`, the page's own tools (pager, Group button), then `{{ template "topbar-end" … }}`. The `topbar` template function (main.go) takes key/value pairs: `Active` nav item, `Title`, `Query`, and so on.
  - The signed-in part (Saved, ★ Favorites, Reading, user menu) is filled by `web/nav.ts` from `/api/me`, so pages stay identical for everyone and cacheable. The last answer (`cf-me`) and the markup it made (`cf-nav`) are kept in localStorage; a small inline script in `topbar.html` puts `cf-nav` in as soon as the bar is parsed (module scripts wait for the whole page), and `nav.ts` redraws only if the answer changed. The page's one `/api/me` request is shared through `web/me.ts`; on the grids it asks `?reading=1`, which adds the marks (`userReading`), so the grid's first look needs no `/api/me/reading` (later refreshes still use it). `nav.ts` also opens and closes the ☰ menu, user menu and mobile search.
  - Wide screens show everything inline. At 1000px or less the browse links move into ☰; at 640px or less search becomes an icon and Saved/Favorites/Reading move into the user menu.
  - A book page opened directly (no `HX-Request` header) gets the bar; the modal's copy doesn't (`Vary: HX-Request`).
- **Scroll engine.** `web/app-htmx.ts` drives the main library, filtered views and search.
  - **One grid, addressed by book index.** Pages are only how the data arrives. Every row is the same height (cards have a fixed aspect ratio), so row `r` starts at `r × rowH`, and a book's place follows from its index and the column count. `measure()` reads both from the layout.
  - **Only the rows around the screen are in the DOM**, between two `.grid-spacer`s sized to the rows they stand for. Moving the window adds and removes rows at its edges and resizes the spacers by the same amount, so nothing on screen moves and there's no scroll compensation. The spacers are painted as empty cards: a CSS mask of one row, built from the measured layout and repeated down.
  - **Books whose page hasn't arrived are `.skeleton` cards**, replaced in place when it does.
  - **Fetching.** Up to 2 pages at a time: the screen first, then ahead in the scroll direction (at least 2 screens, more at speed: 2 fetch-times of scrolling), then behind. Pages no longer wanted are aborted. While pages go by faster than they can be fetched, nothing is fetched until scrolling stops.
  - **Position.** The URL has `?page`, the page of the top row's last book (so going to page N shows N). `history.state` has the exact place: `at` (first book of the top row) and `frac` (how far into that row). A reload or back/forward on the same `?page` returns there. A width change keeps `at` at the top: a `ResizeObserver` lays out again after layout and before paint.
- **Data source.** Each page's HTML sets attributes on `#books`:
  - `data-page-url`: a URL template with `{n}` for the page number
  - `data-page-size` (`booksPerPage`)
  - `data-total-books`
  - `data-empty-text`

  The same script therefore works with the static JSON files and with the API endpoints.
- **Book popup** (`web/modal.ts`) loads `/book/get/<uuid>` through htmx.
  - **Preloading.** Hovering a card preloads the book (`hx-preload`). The card's click is only the hash change (`hx-trigger="none"`). `loadBook` makes the one request with the card as htmx's `source`, which reuses the preload even while it's still in flight, and fetches the per-user controls (`/book/me/<uuid>`, `prefetchControls` in `web/user.ts`) alongside it rather than after it. They aren't fetched on hover: the cover buttons work from the grid's marks (`web/reading.ts`). Once loaded, `user.ts` reports what they show (`cf:book-state`) and the grid fetches its marks again if they disagree; changes saved in the popup (`cf:status`) and with the cover buttons are applied to the marks in place, not fetched again (a book newly marked "reading" is: its resume link and progress come from the server). The grid also fetches its marks every 2 minutes while the tab is shown.
  - **Left and right** (`step`; the arrow keys, the `.modal-nav` buttons `setupModal` adds, hidden when there's no book that way and moved into the book's `.book-page-cover` on narrow screens after each load (`updateNavButtons`), and a quick sideways swipe on the popup that didn't start on something scrolling sideways itself): the card beside the shown one in its grid or row (`neighbour`: DOM siblings, so a skeleton whose page hasn't arrived stops it). The URL's hash is replaced (`history.replaceState`, so no `hashchange`/`popstate`, and back still closes the popup) and the card scrolled on screen, which keeps the grid's window of cards around it. Once the shown book and its cover images have settled (`checkIdle`), the books either side are fetched (`prefetchBook`: kept 30 s, each use gets a clone of the response, handed to `htmx.ajax` as its `fetch`), with their controls and cover images.
  - **Loading state**: a newly opened popup stays hidden (`.pending`) and a switch keeps the previous book showing until the new one arrives or 100 ms pass (`LOADING_DELAY_MS`), then the throbber shows. Only the book last asked for is swapped in (`htmx:before:swap` drops earlier ones); `htmx:finally:request` ends the loading state.

A wrong guess costs only the shift there'd have been anyway.
  - **Tags and authors**: past `bookPageTagLimit` (10) and `bookPageAuthorLimit` (5) they're rendered with `.more-extra`, hidden until the "+N more" button (`.more-toggle`, handled in user.ts) adds `.show-all` to the list.
  - It's a `#book/<uuid>` history entry, closed by going back. While it's open the grid doesn't write `?page` to the URL: going back only closes it if both entries have the same `?page` (otherwise there's no `hashchange`). The page is written once it closes.
  - The modal follows the URL on both `hashchange` and `popstate`, so back/forward between entries with different `?page` still opens and closes it.
  - htmx's own history is off on these pages (`<meta name="htmx-config" content="history:false">`). Otherwise, on back/forward it re-fetches the page and replaces the whole body, grid included.

## Caching

- **Cover thumbnails** are generated on first request and stored in `-cachedir`. Their URL carries the book's `last_modified` (`?t=`), which a new cover changes, so a thumbnail is sent with `public, max-age=31536000, immutable` and a cover the browser has costs no request. A book with no cover gets a 404 the browser keeps for a day (`noThumb`), so coverless cards don't ask again on every view. The server handles one thumbnail request per core at a time (`imageSem` in `covers.go`, sized by `GOMAXPROCS`, which follows container CPU limits).
  - A request the browser cancels (a cover scrolled away) stops before its next expensive step: waiting for a slot, reading and decoding, scaling, encoding.
  - Its thumbnail goes to a backlog (`thumb_backlog.go`), made one at a time once no thumbnail requests have come in for 2 seconds. A new request stops the backlog's current one, which goes back in the queue.
- **Cover loading in the browser** (`pumpCovers` in `web/app-htmx.ts`): covers on screen first, a few at a time (`maxCovers`: 4 over HTTP/1.1, which leaves room for page JSON under the browser's 6 connections per host; 10 over HTTP/2 or 3; 2–4 when Chromium estimates a 2G/3G link); off-screen covers only start once the viewport is done, and in-flight ones that scroll away are cancelled (by removing `src`) and re-queued. While the book modal loads, grid covers are cancelled and wait until every image in the modal has arrived (`cf:modal-busy` from `web/modal.ts`).
- **Scripts, styles and libraries** (`/static/dist/` and `/static/vendor/`, `assets.go`) are held in memory, gzipped once at startup, and served with `Cache-Control: public, max-age=31536000, immutable`. Their URLs change with their content (a content hash, or the library's version), so returning visitors make no requests for them until a new build. A restart picks up a new build.
- **Book pages** use an `ETag` built from the OPF modification time, the groups version and whether the viewer may edit and the cover's modification time, with `no-cache`: every open revalidates (a cheap 304), so an edit or new cover shows at once.
- **Full covers** (`/cover/`) are revalidated on every request; the book page links them with `?t=` set from `cover.jpg`'s modification time, so a new cover gets a new URL. A new or reverted cover also sets `last_modified` and `has_cover` in `metadata.db` (`coverChanged` in `covers.go`), as Calibre does.
- **Saving a cover** (`coverJPEG` in `cover_upload.go`, which calls `imageutil.CoverJPEG`, for uploads, the cover dialog and import covers alike): a JPEG at most 2560px wide and 5 MB is written byte for byte, never re-compressed, since thumbnails are made from it anyway. Anything else (PNG, WebP, a bigger or wider JPEG) is decoded, scaled down to 2560px wide if wider, and encoded once at quality 92. The cover dialog sends pictures (the EPUB's cover, a lookup's, an upload) as the files they are; only pages it draws are sent as JPEGs it encoded.

## Writes

- **Guards.**
  - Every endpoint that changes the library is wrapped in `requireWrites` (`main.go`), which requires `-allow-writes` and a signed-in admin.
  - The whole server is wrapped in `csrfProtect`, Go's `http.CrossOriginProtection`.
- **Read-only mode** writes only CalibreFast's own caches (`./pages` and `-cachedir`). `metadata.db` is opened read-only then (`calibreDSN`: an SQLite URI with `mode=ro`), and the startup pass that writes the pages always opens it read-only. With `-allow-writes` it's `mode=rw`, which never creates a missing database. The URI form also passes paths with `?` in them through intact. `-watch-dir` is ignored without `-allow-writes`: taking files out of a folder is a change too.

## Watch folder and import queue

`imports.go`. `-watch-dir` books wait outside the library until an admin adds them.

- **Watching** (`folderWatcher.run`): [fsnotify](https://github.com/fsnotify/fsnotify) (inotify, kqueue, ReadDirectoryChangesW) on the folder and each subfolder, since watches aren't recursive; a scan finds new subfolders and they are watched after it. An event schedules a scan (`watchDebounce`), and scans repeat every `watchSettle` only while files are settling, so an idle folder is never read. If a watch can't be set up or kept (`poll`), the folder is scanned every `watchPollInterval` (30 s) instead. `-watch-dir-force-polling` goes straight to that, for mounts whose watches succeed but stay silent, which can't be detected.
- **Scanning** (`folderWatcher.scan`): a walk of the folder. Events only say when to look. A file is finished when its size and modification time have been the same for `watchSettle` (and in at least two scans). Files are grouped by folder and name without extension; a group is taken when all of it is finished. A file that can't be taken is logged once and left until it changes. The walk holds the watcher's lock; staging the finished groups doesn't (`stageAll`), so `/api/imports` (`status`) answers while a big batch comes in, and says how many are `staging`. Groups are staged `-import-workers` at a time (default the CPU threads, at most 8), each listed as soon as it's in; the file moves (a full copy across file systems) are two at a time (`stageIO`), so a hard disk isn't seeking between many large files.
- **The queue** (`importInbox`) is the folders under `<datadir>/imports/<id>/` (`-import-dir`, `importQueueDir`; beside the library on its drive, an add renames the files instead of copying them; `checkImportDir` refuses one overlapping the library or holding `-datadir`): the book's files under their own names, `item.json` (a `pendingImport`: what each file says, and their `mergeMeta` as the starting metadata) and `cover.jpg`. Not in the app database: a waiting book is its folder. A folder without a valid `item.json` is logged and skipped, never deleted.
- **Review** is the metadata editor. `templates/book-edit.html` renders for a waiting book when `EditBookPageData.Import` is set, and the browser code takes a `BookTarget` (`web/book-target.ts`): the addresses for a library book (`libraryBook`) or a waiting one (`pendingImport`). `web/metadata.ts`, `isbn-tools.ts`, `cover-dialog.ts` and `cover-sources.ts` only use those, so both kinds share one editor.
  - `/import/{id}/metadata`, `/isbns`, `/formats`, `/file/{format}`, `/cover`, `/cover/status`, `/cover/revert` mirror the library's endpoints, on the queue's folder. Cover saving is shared (`readCoverUpload`, `saveCoverJPEG`, `revertCoverIn` in `cover_upload.go`).
  - **Series from a placeholder** (`fillFromPlaceholder`, `placeholders.go`): a book uploaded, or put in the import queue, with no series in its files takes the series and number of the placeholder with its title (case, punctuation, a trailing "(Series #n)" and a subtitle on one side only aside) by one of its authors (`hcSharesAuthor`), and that placeholder's Hardcover identifiers. Not when placeholders in different series match. In the queue it's what the review starts with; the placeholder is deleted only when the book is added (`resolvePlaceholders`, which matches titles the same way). The placeholder's metadata is also a source named "Placeholder" (`placeholderSource`): in the import review (`importSources`, looked for when the review opens: `importPlaceholder`), and, kept with the files' sources in `bookMetadataCache`, in the editor of the book an upload or approval added, after the placeholder itself is gone. The upload page names a series it gave (`UploadResult.SeriesFromPlaceholder`) and has **Edit** beside **View** for each added book.
  - **Edited into a placeholder's book** (`placeholder_resolve.go`): when `catalogFlush` rereads changed books (the editor, bulk edits, reverts, Calibre's own changes), a placeholder is deleted if one of them now has its title by one of its authors, its ISBN (`identifiers`), or its title, series and number. Series and number alone aren't enough. The deletion is logged ("placeholder in library"), so it can be undone. Whichever way a book replaces a placeholder (added, approved, or edited into it), `placeholders.replaced_by` keeps its uuid, and the placeholder's page `/missing/<uuid>` redirects there (303) while the book is in metadata.db. Removed by hand, or restored by an undo, it's cleared.
  - **Covers from the files** (`import_covers.go`): `stage` hands the book to a background worker (`coverSoon`, `startCoverWorker`), so it's listed without waiting; at startup every waiting book is handed to it, for those staged without one. `stageForPlaceholder` takes the files' cover at once, before the placeholder's. The EPUB's declared cover (EPUB 3 `cover-image`, EPUB 2 `<meta name="cover">`, or an image item with id `cover`), else the PDF's first page when its largest picture (pdfcpu `ExtractImagesRaw`) is big and has the page's shape (`imageutil.PDFImageIsPage`). Go can't render PDF pages, so pages of text and vectors are left to the browser. Saved as any cover is (`coverJPEG`: the EPUB's or the PDF's own JPEG as it is), and only if there's no `cover.jpg` (`O_EXCL`), so a cover chosen meanwhile is never replaced.
  - `mountCoverDialog`'s `autoDefault` gives a waiting book the server found no cover for the EPUB's cover or the PDF's first page, rendered in the browser. A book with a cover isn't loaded until the cover dialog opens.
  - PDFs are opened for covers with `openPdfRanges` (`web/vendor.ts`): a `PDFDataRangeTransport` whose first read is a 64 KB range (its `Content-Range` gives the size), then only the ranges pdf.js asks for. pdf.js's own loader starts with a request for the whole file and cancels it once it sees ranges work, by which time much of it may have come.
- **File names** in a book's folder are `<title>.<format>` (`bookFileStem`), the same as `data.name` in `metadata.db`: Calibre finds a format's file as `<path>/<name>.<format>`. If that name is taken, the file gets a suffix and `data.name` is updated to match. Older versions recorded the uploaded file's own name instead; `repairFormatNames` (`calibre_names.go`) points each such row at the one file in the folder with that format's extension (metadata.db only, never the files). It runs only from the Library repairs page (`library_repairs.go`, `/admin/repairs`, behind `requireWrites`): `GET /api/admin/repairs` lists what it and `addUnlistedFormats` would change, `POST /api/admin/repairs/format-names` repairs. Both functions also refuse without `-allow-writes` (`errReadOnly`). Nothing runs at startup: checking stats every format's file.
- **Duplicates** (`duplicates.go`, `findDuplicates`): books with the same title (`COLLATE NOCASE`); a match is one with the same authors, or one holding a byte-identical file (same format and size, then SHA-256, cached by path, size and mtime: `pkg/filehash`). `findDuplicatesISBN` (new files for a book) also takes books with one of the given ISBNs (`identifiers` of type `isbn`, compared without separators as ISBN-13 and ISBN-10: `isbnForms`), which match by that alone (`SameISBN`). Uploads (`processUploadGroup`) and `approve` refuse a match (`UploadResult.Duplicate`, or 409 with `duplicate`) unless sent again with `override`, which never adds an identical file. The editor page (`EditBookPageData.Duplicates`), `approve` and Discard Existing Files (`/import/{id}/discard-identical`, one request per book from the page) check metadata.db. `/api/imports` shows the same check made in the background against the in-memory catalog (`dupIndex`: books by title, as `trim` and `NOCASE` compare them, built from `currentCatalog()` without reading the disk; only the candidates' `data` rows come from metadata.db), so a queue of hundreds doesn't scan the books table once per book over the single connection. Each result is kept with the catalog it was made against, and checked again in the background when the catalog changes, the old one shown meanwhile. File hashes are kept in memory (`pkg/filehash`, least recently used dropped past 50000), so a recheck doesn't read the files again.
- **Quick edits** (`imports_edit.go`): `/import/edit` is the bulk editor's page in queue mode (`library-edit.html` with `.Queue`; `web/library-edit.ts` reads `data-source="queue"`: its rows from `GET /api/imports/table`, edits to `POST /api/imports/bulk`, a Library column, no merging, removing or not-duplicate marks). Rows are `tableBook`s made from each waiting book's `Merged` (`uuid` is the queue id; `Into` items left out), with `Library` from the cached duplicate check. An edit is `bulkEdit.apply` on a copy of the item, under `importInbox.mu`: a book taken for adding or discarding isn't edited, and the copy replaces the old item, so a reader holding the old one (Mass Import) reads it whole. The edit is committed to calibrefast.db first (`import_edit_journal`, the item's `Merged`; `imports_edit_queue.go`) and the editor answered; a writer then writes the item.json whole (`writeItemJSON`: temporary file, sync, rename) in the background, so a slow `-import-dir` doesn't hold up the editor or the queue (it holds `flushMu`, not `mu`). Taking a book holds `flushMu`, so no write of it is under way: discarding writes its pending edits into its item.json first, adding and splitting drop them (they went in with the book, or the split starts again from the files). On start `replayImportEdits` puts journalled edits back on their books before anything reads the queue; rows for books no longer in the folder are dropped, others kept. The series is written to `Merged.Meta` too (`SyncSeriesMeta`), which is where `approve` takes it from. Changed title or authors drop the item's duplicate result (`forgetDuplicates`) and start a recheck; each result also remembers the item it was made for (`dupResult.it`), so a check of the old copy finishing late is never shown for the new one. `Sources` are untouched. Not in the edit log: the library isn't changed, and adding the book is logged as before.
- **Adding** (`POST /import/{id}/apply` → `importInbox.approve`): `addBook` (`add_journal.go`, shared with uploads: the files and the cover go into a staging folder in the library, the rows are inserted, and just before the commit the staging folder is renamed to the book's folder; undone if a step fails, with the files moved back), then `updateBookInCalibreDB`, the same write as the editor's Apply, and the queue folder is removed. The book is taken out of the queue first, so two requests can't both add it, and put back if adding fails.
- **Crash safety** (`add_journal.go`): every add writes a journal in `<library>/.calibrefast-adding/` before touching anything. At startup (`recoverInterruptedAdds`, with `-allow-writes`) each journal left behind is settled: if `metadata.db` has the book (id and uuid) the add committed and its last steps are finished (the import's metadata, its queue folder); otherwise the book's folder and files go back where they came from. A file is deleted only where another whole copy is kept; `moveFile` copies across filesystems to a `.partial` name and renames it into place, so an interrupted copy is never mistaken for a whole one.
- **Mass import** (`imports_accept.go`, `web/imports.ts`): one `POST /import/{id}/accept` at a time, each checked against the library as it is after the last. The page finds covers `COVERS_AHEAD` books ahead while the server adds one, and doesn't wait for the library pages' rewrite every 25 books. The server reads a book's files for a cover only if its cover worker hasn't already (`coverFromFiles`). An add taking a second or more is logged with its steps (`addTiming`: the duplicate check, the files, the database, the last steps), to tell a copy across drives from a busy database.
- `/api/me` reports `pending_imports` to admins, for the top bar (`web/nav.ts`). `/import` is `templates/imports.html` and `web/imports.ts`, which polls `/api/imports`.

## Merging books and the bulk editor

- **Merging** (`merge.go`). `/book/merge?ids=a,b&keep=a` renders `book-edit.html` with `EditBookPageData.Merge` (its `Formats` compare same-format files with `filehash.SHA256`, cached by path, size and mtime; each choice carries the start of its hash, so the page says per format whose bookmarks and highlights won't carry over); the browser takes `mergeBooks()` (`web/book-target.ts`), whose `metadata` is `/merge/metadata` (`mergeSources`: the kept book's OPF as `current`, the others' by letter, then `readBookMeta` of every file) and whose `extra()` adds the merge's choices (keep, uuids, cover, format → uuid) to what `applyValues` posts to `/merge/apply`. `mergeBooks` (under `bulkMu`) → `mergeInto`:
  1. hashes the file kept in each format, and notes, per other book, the formats whose file is that one byte for byte (before anything moves); copies the chosen files and cover into the kept book's folder under `.cf-merge-*` names (none for a file identical to the kept book's own);
  2. `recycleBooks` the others (all or nothing; on failure the copies are removed). With no other library books (adding files, below) a batch is made only if a file is replaced (`recycleBatch.create`);
  3. renames the copies into place: a format the kept book has keeps its file name (`data.name`), the old file going to the batch as a `recycledFormat` (`Replaced`) with the kept book's bookmarks and highlights in that format (`takeFormatRows`); a new format gets a `data` row named as the book's others;
  4. `mergeReaderData`: `INSERT … SELECT` of the other books' rows in each reader table to the kept uuid (newest wins for `reading_status` and `reading_progress`, every format); bookmarks and annotations only in the formats noted in step 1, with a suffixed `client_id`, as theirs is the primary key. It answers how many weren't carried over (`mergeResult.Dropped`, logged);
  5. `updateBookInCalibreDB` with the form's values, then `batch.MergedInto` (`mergeNote`) is saved.

  After step 4, `noteMerged` (`book_redirects.go`) stores old uuid → kept uuid in `book_redirects` (app database), re-pointing earlier redirects to the merged-away books so there are no chains; restoring a book from the bin drops its redirect (`forgetRedirect`). The book page (`bookHandler`, so the popup too), the readers (`/read`, `/read-pdf`) and downloads call `redirectMerged` only when the uuid isn't in the library: a 302 (not permanent: a restore undoes it) to the same address with the uuid replaced in the path or `?uuid=`.
- **Adding files to a book** (`add_format.go`). `POST /book/add-format/{uuid}` (multipart `files`, one per format, book extensions only) leaves out a file identical to the book's own in its format (409 if nothing is left), and stages the rest in the import queue (`importInbox.stage` with `into`: `pendingImport.Into`), so an unreviewed upload stays listed at `/import` (its row links the review; `/import/{id}` redirects there; `nextImport` skips it). `GET /book/add-format/{uuid}/{id}` is the merge page with the book (`loadMergeBook`) and `incomingMergeBook` (UUID `incomingUUID`, `Import` set: its cover and files are the queue's URLs) as the two books, the new files chosen by default; `mergePageData.Incoming` switches the page's wording, adds **Add files, keep metadata** (submits the form as loaded), and hides "Keep this record". `EditBookPageData.Duplicates` is `incomingDuplicates`: `findDuplicatesISBN` with the new files' title, authors and ISBNs, excluding the book; each match links `/book/merge?ids=<book>,<match>&keep=<book>`. `…/metadata` is `mergeSources` (the incoming book has no OPF; its files are `New epub`…). `…/apply` takes the item from the queue, refuses (409, `duplicate`) when another book holds an identical file (`web/metadata.ts` then offers that merge), and runs `addFormats` → `mergeInto`; the item's folder goes once added, and it's put back if nothing was done. The browser side is `addFiles()` in `web/book-target.ts`, and the book page's Files row is `web/book-files.ts`.

  A failure after step 2 doesn't undo it: the answer is 200 with `warning`, which the editor shows.
- **Bulk editor** (`bulk_edit.go`, `templates/library-edit.html`, `web/library-edit.ts`). `GET /api/library/table` is every book as a `tableBook`, one query with `group_concat` subqueries; a book with no `data` rows gets its folder's formats (`folderFormats`, through `resolveFormats`) and `formats_from_folder`. `loadMergeBooks` falls back the same way. `POST /api/library/repair-formats` (`addUnlistedFormats` in `calibre_names.go`) adds `data` rows for those books: one per format with exactly one file in the folder, `name` its file name without the extension. The browser does filtering, sorting and duplicate grouping, and draws only the rows on screen (fixed 34px rows, absolutely placed in a body as tall as all of them). `POST /api/library/bulk` takes uuids and a `bulkEdit` (set, add or remove fields), applies it to each book's `metadata.opf` (`bookEditMetadata`) and saves changed ones with `updateBookInCalibreDB`, then answers the changed rows. The library's edits go through a queue (`bulk_queue.go`) so the editor doesn't wait on slow storage: the handler commits the edit and its books (`bulk_edit_queue`, `bulk_edit_books`) to calibrefast.db and answers `202` at once with the rows as it will leave them (`predictRow`) and a job id; one worker makes the queued edits in order, a book at a time under `bulkMu`. Safety over completeness: each book records the `last_modified` it was queued against, and the write checks it in its own transaction (`updateBookIfUnchanged`), so a book changed elsewhere meanwhile fails instead of being written over (a later queued edit to the same book is checked against what the earlier one left). Each book's outcome is committed as it's made, so after a stop or crash only books without one are made, with the same check. Failures are kept in `bulk_edit_failures` until an editor dismisses them in the bulk editor; a panic is the book's failure. Until a book's edits are written, `GET /api/library/table` shows its foreseen row; `GET /api/library/bulk/jobs?ids=` reports progress and results (the page shows "Saving…"). Other library writes (the metadata editor, merges, removals, undo, format repairs) wait for the queue first (`afterBulkEdits`, `afterBookEdits`), and are refused (503) once the server is stopping rather than made ahead of it.
- **Not duplicates** (`not_duplicates.go`): sets of book uuids an admin marked as different books (`not_duplicate_sets`, `not_duplicate_books` in the app database), sent with the table. The browser hides a look-alike group only when one set holds every book in it, so a newcomer brings the group back; `dupes=marked` shows the sets, `DELETE /api/library/not-duplicates/{id}` unmarks one.
- **Grid pages after edits** (`refreshLibraryPages`): the pages are written again from the catalog, and only the files whose contents change are replaced, so the grid shows new titles and authors at once.

## Removing books and the Recycling Bin

`recycle.go`; behaviour in [FEATURES.md](FEATURES.md#removing-books-and-the-recycling-bin).

- **Removing** (`POST /api/library/delete` → `recycleBooks`): under `recycleMu`, a new batch folder; `VACUUM INTO` copies `metadata.db` there first (no copy, no removal). Then each book's folder is moved in (`moveDir`: a rename, or copy and remove across filesystems), then one transaction deletes the rows (`deleteBooksFromCalibreDB`). A failed move or delete moves the folders back and drops the batch.
  - **Rows:** every table with a `book` column (`tablesReferringToBooks`, from `sqlite_master`, skipping virtual tables), so custom columns and tables newer Calibre versions add go too; then authors, publishers, series and tags nothing links to.
  - `books.path` is checked to be strictly inside the library (`libraryBookDir`): an empty path would be the whole library.
- **Restoring** (`POST /api/recycle-bin/{batch}/restore` → `restoreRecycled`): the folder moves back, then `restoreBookRows` attaches the batch's `metadata.db` as `bak` on a connection of its own and copies the book's rows in one transaction: the `books` row (its old id unless taken; then the uuid set back, since Calibre's insert trigger replaces it), plain tables with `book` changed, and link tables through `linkedEntityOf`, which maps each linked item to the library's by name (`restoreEntity`), copying it from `bak` when missing. Restored books are marked in `batch.json`.
- **Calibre's full-text tables.** `metadata.db` has FTS5 indexes of annotations (`annotations_fts`, `annotations_fts_stemmed`), kept by Calibre's triggers, and `books_delete_trg` deletes a book's annotations: so removing any book, and restoring one, writes to them. go-sqlite3 has FTS5 only with `-tags sqlite_fts5`. `checkVirtualTables` opens every virtual table first (at startup with `-allow-writes`, before a removal and a restore) and refuses with how to build, rather than failing halfway.
- **Readers' data** (`recycle_userdata.go`): removal leaves `calibrefast.db` alone; the batch gets `reader-data.json`, the rows of `readerDataTables` (bookmarks, annotations, reading_progress, reading_status, favorites, shelf_books) for its books. Restoring inserts them `OR IGNORE` (a live row with the same key is newer), skipping rows whose user or shelf is gone.
- **Afterwards** only the page files holding the books are rewritten (`library_pages.go`; `bookPages` remembers which pages hold each book, `pagesMu` serializes page writes). A removed book leaves a gap at the end of its page and `totalBooks` stays the same, so no other page shifts; the grid shows the gap as an empty slot. A book restored in the same run goes back to its old place; one removed before a restart goes at the end of the last page. The next startup writes every page in order again. Both also clear the per-book caches (`forgetBook`) and refresh the overviews.
- **Single files** (`recycle_formats.go`): a batch's `Formats` are files taken from books that stay in the library, under `<batch>/formats/` with their readers' rows in that format beside them (`<file>.reader-data.json`, `collectReaderRows`/`writeReaderRows` from `recycle_userdata.go`). `POST /api/library/books/{uuid}/formats/{format}/remove` (`recycleFormat`, under `bulkMu` then `recycleMu`) makes a batch (`metadata.db` copy first), moves the file, deletes its `data` row, then takes `formatReaderTables` (bookmarks, annotations, reading_progress) rows in that format and forgets the book's KOReader hashes (`formatsChanged`). It refuses the book's last file (409, `last`: the browser removes the book instead, with a warning) and a format with several files in the folder. A replaced file (merge or new file) takes only bookmarks and annotations: places are kept. Restoring (`restoreFromBin` with `formats`: `"<uuid>/<FORMAT>"`; with neither uuids nor formats, everything in the batch) needs the book in the library without a file in that format: the file moves back under its old name, gets a `data` row named after it, and the rows come back `OR IGNORE` (`restoreReaderRows`).
- **No web endpoint deletes from the bin.** `-empty-recycle-bin` (`emptyRecycleBin`) runs from the command line and exits.
- **Browser:** `web/delete-books.ts` is the confirmation (type `delete`) and Undo; `web/select-books.ts` adds **Select** to the grid's top bar (and a long press on a card, touch and pen only, which swallows the click that follows) once `nav.ts` says the viewer can edit (`data-can-edit` on `<html>`, `cf:me` event), and marks cards as `app-htmx.ts` renders them; `web/user.ts` wires the book page's button; `web/recycle-bin.ts` is `/recycle-bin`.

## ISBNs and online lookups

Both are behind `requireWrites` and only add options to the metadata editor (`web/isbn-tools.ts`). They never write.

- **`/metadata/{uuid}/isbns`** (`isbn.go`, with the work in `pkg/isbn`) finds ISBNs in the book's files. GET reads EPUB (package identifiers, then the first 5 and last 3 spine documents' visible text), MOBI and AZW3 (EXTH record 104). It names the book's PDF, if any.
  - Go has no reliable PDF text extraction, so the editor reads the PDF with pdf.js: the XMP packet and the first and last few pages, with range requests and `disableAutoFetch`. It POSTs them to the same endpoint.
  - All parsing, check digits, ISBN-13 normalisation, labels and ranking happen on the server, so there's one implementation.
- **`/metadata/lookup?source=openlibrary|google|hardcover&isbn=…`** (or `&title=…&author=…`) (`lookup.go`; the clients are `pkg/metalookup`) asks one source per request and answers a list of `matches`, best first, each an `UploadedBookMeta` (Format "Open Library", "Google Books" or "Hardcover") and its cover. The editor's lookup bar (`web/isbn-tools.ts`) asks Open Library by ISBN (its box follows the form's ISBN field, and a valid ISBN searched there fills it) or by title and author, a button each; Google only on **Try Google Books**, Hardcover only on **Try Hardcover**. Each match the admin ticks is added as a source with `External` set and its own Format ("Open Library", "Open Library 2", …); unticking removes that Format. Lookup sources with the same value for a field share one pill (`data-formats` lists them; `web/metadata.ts`), which goes when its last source does.
  - **Open Library:** `/isbn/{isbn}.json` (the edition), then its work (description, subjects) and authors: one match. Without an ISBN, `/search.json` with `limit=5`, then those works at once for their descriptions: up to 5 matches, no ISBNs (a work is all its editions). The search's edition ISBNs stay on the server: `&match_isbn=` sets `hasIsbn` on the matches with an edition of it (on a copy of the cached answer), and the editor ticks those, or a search's only match.
  - **Google Books:** `/volumes?q=isbn:…`, with `CF_GOOGLE_BOOKS_KEY`. Only offered and answered with that key (`googleBooksEnabled`): the shared quota without one is usually used up. No covers.
  - **Hardcover** (`lookup_hardcover.go`; `LookupBooks` in `pkg/hardcover/books.go`), with `CF_HARDCOVER_TOKEN` (`hardcoverEnabled`): by ISBN, the edition with that ISBN-13 (or its ISBN-10) and its book; else Hardcover's book search for the title and author, then up to 5 of its books. Two requests either way, through the same `hardcover.Budget` as series (over it, the lookup answers with an error naming when to try again; it isn't queued). A match has the authors (in Hardcover's order), the featured series and its number, up to 8 Genre tags, the description (plain text, escaped into paragraphs), an edition's publisher, date and language, and the identifier `hardcover:<slug>` (as Calibre's Hardcover plugin names it). Covers: `/metadata/lookup/cover?src=hardcover&id=<book id>` fetches the image URL the lookup's answer gave, kept on the server by book id; only `https` on `hardcover.app`, raster types only (no SVG), without the token, and redirects only within `hardcover.app`.
  - Answers, including "no match", are cached in memory for 24 hours (500 entries). Errors aren't.
  - **Limits** (`metalookup.Limiter`, one per site): a token bucket and a daily cap (Open Library 20 then 1/s, 1,000 a day; Google 5 then 1 per 10s, 100 a day). A 429 pauses that site for its `Retry-After`. Over a limit, requests are refused with a message, not queued.
  - Requests carry `User-Agent: CalibreFast/<version> (+https://github.com/iotku/CalibreFast)` and nothing about the library or user. `-no-lookups` refuses both endpoints and hides the lookup; `-no-google-books`, or no `CF_GOOGLE_BOOKS_KEY`, refuses Google and hides **Try Google Books**; `-no-hardcover`, or no `CF_HARDCOVER_TOKEN`, does the same for Hardcover.
- **`/metadata/lookup/cover?src=openlibrary&id=…`** fetches a lookup's cover for the editor's cover dialog (`web/cover-dialog.ts`), only when the admin clicks **Look up cover online**. That button asks `/metadata/lookup?source=openlibrary` for the ISBN in the form's ISBN field (cached, so a later lookup of it is free) and adds the covers of the ticked matches. The server builds the URL from a cover id it checks, so it can't be pointed elsewhere. The browser never contacts the third party.

### Hardcover series

`hardcover.go`, `hardcover_match.go`, `hardcover_http.go`; client in `pkg/hardcover`. Off unless `CF_HARDCOVER_TOKEN` is set (and not `-no-hardcover` / `-no-lookups`). Editors only.

- **Links:** `hardcover_series` maps a series as browsed (its group's name, so a group links once) to Hardcover. It keeps the last fetched list (`snapshot`, JSON `hardcover.SeriesDetail`) and `checked_at`.
- **Parts:** Hardcover splits some series into one per author, all with the same name and numbered as one ("Doctor Who: Target Books"). So a series links to every row of `hardcover_series_parts`, and `SeriesBooks` fetches them all in one request and merges them. Two parts' books at the same position are one entry: the most-read one is shown, and the others' titles (`AltTitles`) and ISBNs count for matching. Candidates are grouped by name (`hcSeriesKey`, which keeps what follows a colon). `SeriesByName` finds the parts a search's ten results leave out. The likeliest group is ticked as a whole: same name as the library's series with evidence (ISBNs, the author, or a title), else the most library ISBNs. A batch links it only when the name is the same, or when it holds at least 3 of the library's ISBNs and more than twice as many as any other group.
- **Queue:** every request to Hardcover is a row of `hardcover_jobs` (`candidates`, `link`, `refresh`, `batch`), run one at a time by one worker (`hcStep`). When `hardcover.Budget` says to wait (plan limits, or a 429), the job and every job behind it become `held` with `not_before`. Nothing fails for lack of budget. The budget's day is saved in `hardcover_usage` and restored at start; a job left `running` is queued again. Clicks wait up to 5 s for their job, then the page polls `/api/hardcover/jobs`.
- **Review:** `hcMatchSeries` matches the list against the catalog (ISBN via metadata.db `identifiers`, then the same title in the series, then title plus a shared author, then title only as weak) and against placeholders (`hardcover-id` identifier, series and number, or title and author). It sorts entries into *in the library*, *in the library without the series* (tag via `queueBulkEdit`, one book per job), *not in the library* (placeholders with `source = 'hardcover'` and the identifiers `hardcover-id:<book id>` and `hardcover:<slug>`) and *not on Hardcover's list*. Whole-number positions are ticked; novellas (1.5) and unnumbered books are not. A placeholder's page and popup link to `https://hardcover.app/books/<slug>` (`hcMetaURL`, `hardcover_ids.go`): its `hardcover` slug, or for one with only `hardcover-id` (made before slugs were kept) the slug of that id in its series' saved list. Editing a placeholder keeps those identifiers (the form has only the ISBN), and the book that replaces it gets them (`withPlaceholder`).
- **Dismissals:** `hardcover_dismissed` (series name, Hardcover book id) holds what an editor turned down ("Not in this series", a renumbering, a wrong match). It outlives refreshes, relinks and unlinking. An entry merged from several parts counts as dismissed when any of its books is (`Entry.AltIDs`), since which one is shown can change between fetches. Dismissed rows are listed apart on the review page, each with Restore. "Not a match" on a row in *in the library without the series* (its only button: a wrong match there needs a placeholder, not a dismissal) records the pair in `hardcover_not_match` (series, Hardcover book id, library uuid): that book is never matched to that entry again (`hcLibrary.refuses`, any of the entry's merged ids), and the entry gets a placeholder unless one already stands for it. Refused pairs are listed with the dismissed; Restore match (or Restore all) deletes the pair, and any placeholder made for it stays.
- **Completion:** a linked series is complete when every whole-numbered entry not dismissed is in the library and tagged with the series (`hcReview.Numbered`/`Have`). A placeholder doesn't count, and neither does a book here without the series. See "Complete series" below for how it's shown, and for the manual way that needs no token.
- **Pages:** `/missing/hardcover?series=` (link, refresh, review, apply), `/missing/hardcover/author?author=` (a batch of that author's series, at most 25), and a card on `/missing`. Series and author pages link to them (`FilteredPageData.Hardcover`).

### Author profiles from Hardcover

`hardcover_authors.go`; client in `pkg/hardcover/authors.go`. The top of an author's page (`agg-header` in `templates/author-profile.html`) shows Hardcover's picture, bio and years where the entry has no description or picture of its own (`aggregate_meta` wins, field by field), with a link to their Hardcover page.

- **On demand, kept for good:** the page carries `data-profile-lookup` when a signed-in user opens it and the author was never looked up. `web/author-profile.ts` POSTs `/api/authors/profile?name=`, which queues an `author` job (only for authors with books here), waits up to `hcAwaitTime`, and answers the header rendered again (200) or 202 while it waits; then it shows on the next visit. What Hardcover answers, found (`hc_id` > 0) or not (0), stays in `hardcover_authors` and is never asked again; a failed lookup (`hc_id` -1) may be retried after a day. Editors get **Look up again** (`/api/authors/profile/refresh`). Pictures are fetched once (only `https` on `hardcover.app`, raster only, without the token), re-encoded as JPEG into `<datadir>/author-images` and served from there.
- **Matching:** `AuthorsByName` with the name's spellings (`hcAuthorNameVariants`: "Last, First", initials with and without spaces), one request; if none, `SearchAuthors` keeping hits whose name or alternate name is the same (`hcNameKey`) and `AuthorsByID`, two more. Of several, the one with most of the library's titles among their 40 most read books, else one only if far more read than the next (`hcPickAuthor`). Bios are made plain text (tags and footnote marks dropped) and shown escaped, the first part with the rest behind **More**.
- **Budget:** author jobs share the Hardcover queue but run after every editor request, at most one every `hcAuthorSpacing` (20 s), so a backlog trickles out. They leave the last `hcAuthorReserve` (20%) of the day's limit to editors: past that, author jobs alone are held until the limit resets (`hcAuthorHeld`), then go out one at a time again. They aren't listed among the series requests.

### Reading sync to users' Hardcover accounts

`hardcover_link.go` (linking), `hardcover_sync.go` (sending), `secretbox.go` (tokens at rest); client in `pkg/hardcover/oauth.go` and `library.go`. On unless `-no-hardcover-sync`/`-no-hardcover`, or no OAuth client id (`CF_HARDCOVER_CLIENT_ID`; none ships with CalibreFast, each server registers its own app). It needs no `-allow-writes` and no `CF_HARDCOVER_TOKEN`.

- **Linking:** `POST /account/hardcover` (`action=link`) starts a device grant and keeps it in memory (`hcSync.pending`); a goroutine polls the token endpoint, asks `me`, and stores the link in `hardcover_links` with both tokens sealed. The account page shows the code; `web/hardcover-link.ts` polls `GET /api/me/hardcover` and reloads when it's done. `action=settings` saves which books and what to share; `action=unlink` (allowed even with sync off, through `hcRevoker`) revokes and deletes the link, the queue and the choices, and says if Hardcover couldn't be told; `adminDeleteUser` unlinks first too; `action=backfill` (sharing every book) queues the user's reading and finished books.
- **Consent:** nothing is queued or sent for a book unless the user shared it (`hardcover_shared`, from **Track on Hardcover** in `book-user-actions.html` → `PUT /api/me/books/{uuid}/hardcover`) or shares every book (`hardcover_links.share_all`). Progress and dates go only with `share_progress` / `share_dates`. `hcShared` is checked when a change is noted and again before sending; unsharing a book, or going back from every book to chosen ones, drops what waited. A merge carries a user's choice to the book kept.
- **Changes:** `hcSyncStatus` (from `setStatus`/`setManualStatus`) and `hcSyncTouch` (progress from the web readers, KOReader and guest import; merges) upsert a row of `hardcover_sync` with `due_at`, only for linked users (an in-memory set) and shared books. A status is due now; progress after `hcProgressDelay` (3 min), never later than a time already set, so steady reading still goes every few minutes. `changes` counts upserts, so one made while the book is being sent keeps it due. The row also keeps the local dates a read started and finished.
- **Sending:** one worker (`hcSyncStep`) takes the row due longest among working links. `hcPushBook` reads the book's state *now* (`readStatus`, `latestProgress`), so many changes go as one: find the Hardcover book and edition (`hcResolveBook`: ISBN-13s, then `hardcover-id`, then the `hardcover` slug; kept in `hardcover_books`, 30 days found, 7 not), the user's entry, then add it or change its status (1 want to read, 2 reading, 3 read; Hardcover starts and finishes reads itself), then the read's `progress_pages` (percent × the entry's edition pages, at most one short of the end, since reaching it would finish the read there) and dates. A cleared status is not sent. A `WaitError` holds all of that user's rows until it ends; other errors back off ×4 from a minute to a day; a book not on Hardcover is set aside with a note shown on the account page.
- **Tokens:** a `hardcover.Client` per user with `Config.TokenFunc` (`hcTokenFunc`): the stored access token, renewed a day before it expires or after a 401, one renewal at a time, the new pair stored before use. Refused renewal marks the link `broken` and deletes its tokens. Each client has its own `Budget` (limits are per token).

### Complete series

`series_complete.go`. A series is complete when the library has every whole-numbered book (1, 2, 3…). Two sources, either enough on its own: what an editor said (`series_verified`, set with "Mark complete" on the series page; no online service needed), or the series' Hardcover list (above). An editor's word wins. They give the series' highest number (`total`: every whole number up to it is needed; a book numbered past it raises it, so a series that grew is complete again once the library has the new books too), its number of books whatever their numbers (`books`, for series whose books are all #1 or #0), or both, and both must hold. Placeholders aren't books the library has: 10 books with 8 here and 2 placeholders is 8 of 10. On `/missing` (`series_gaps.go`) the numbers it lacks show as gaps, and so do books short of the count, placeholders standing in for missing ones (not for a group's members, each only part of the series). `seriesStatuses` caches every status and works them out again only when the catalog, `aggregateGen` or `seriesStatusVersion` (links, dismissals, counts) moves. `/series` marks complete series and filters them (`?complete=1`); so do author pages' series chips, the series page header and the Hardcover pages.

## KOReader progress sync

[KOREADER.md](KOREADER.md) covers setup. Under the hood:
- `kosync_server.go`: KOReader's sync API under `/kosync` (protocol pieces in `pkg/kosync`), the per-user sync keys, and joining device positions with the web readers'.
  - Devices authenticate with headers, so `/kosync/` is a public path to `withAuth`.
  - Device positions are kept raw in `device_progress`, one per (user, document id), last writer wins, as KOReader's reference server does.
  - Nothing is copied between `device_progress` and `reading_progress`. Each read (the web reader's `GET /api/me/progress`, a device's `GET /kosync/syncs/progress/…`) takes the newest of the two for that book format and converts it.
- `kosync_digest.go`: maps KOReader's document ids to library files (`book_uuid`, format). The hashes themselves are `kosync.PartialMD5` and `kosync.FileNameDigest`.
  - **Binary ids:** KOReader's partial MD5. It's computed lazily, when a file is opened in the web reader or downloaded, and cached in `book_digests` with the file's size and mtime, so a changed file is hashed again.
  - **Filename ids:** the MD5 of the file name. They come from Calibre's `data` table, rebuilt in memory at most once a minute.
  - When a device asks about an id nothing matches, the files the user has read on the web but never hashed are hashed in the background.
- `pkg/koreader` (`epub.go`): EPUB position translation (`koreader.XPointerToCFI`, `koreader.CFIToXPointer`).
  - KOReader's `/body/DocFragment[N]/…` XPointer and the web reader's CFI both name the spine item: DocFragment N is the N-th spine itemref with a manifest entry.
  - Inside the chapter, the element path is followed in the chapter's XHTML. It converts to that element when the path resolves, otherwise to the chapter start. Character offsets are dropped.
  - PDF positions are page numbers on both sides.
